# Memory System - Implementation Plan

## Architecture

The memory system is a separate Go process that communicates with opencode via stdin/stdout JSON-RPC. It exposes an MCP server with tools for reading and writing memory. Data persists in SQLite with WAL mode and separate reader/writer connections.

```
opencode agent
    |
    | (post-turn hook)
    v
MCP Server (Go, stdin/stdout JSON-RPC)
    |
    +--> Writer: analyze turn -> update PFC -> promote to HC -> promote to NC
    |
    +--> Reader: query neocortex by keywords, return ranked results
    |
    v
SQLite (WAL mode, separate reader/writer connections)
```

## Key Behaviors

### Prefrontal Cortex (active context)

The PFC is an in-memory ring buffer of items. Each item tracks content, a score, a weight, a rate, a tick count, and a creation timestamp.

When the writer processes a turn:

1. The LLM compares new context against existing PFC items using semantic matching to identify which items are being "reused."
2. Reused items have their tick count reset to zero, their content updated if changed, and their weight blended (70% original, 30% new LLM assessment).
3. New items are added with an LLM-assigned rate and weight. Their score starts at the weight value (since tick count is zero).
4. All items in the PFC advance one tick (global counter).
5. Items whose score drops below 0.5 are evicted.
6. Items whose score rises above 0.7 are promoted to the hippocampus.

### Hippocampus (short-term)

The hippocampus is a SQLite table that stores items promoted from the PFC. It provides longer-term retention while still being subject to decay.

When the writer processes hippocampal items:

1. Items whose score drops below 0.3 are forgotten (deleted).
2. Items whose score rises above 0.7 are promoted to the neocortex.

### Neocortex (long-term)

The neocortex is a SQLite table that stores memories for the long term. Each entry has content and a JSON array of keywords. Keywords are generated by a hybrid approach: the LLM extracts primary keywords, with statistical extraction as a backup for coverage.

At evaluation time (end of each turn's pipeline), hippocampal items are assessed by the LLM for usefulness. Useful items are stored in the neocortex. Items with a final score below 0.6 at evaluation are forgotten.

### Memory Reader

The reader takes an arbitrary query and searches the neocortex using hybrid search: keyword matching first, then semantic re-ranking for top results. It returns memories ranked by relevance score.

### Memory Writer

The writer receives the latest turn and current PFC state. It makes a single LLM call per turn to: analyze what is worth remembering, determine which PFC items are reused, extract keywords for neocortex-bound items, and assign rates and weights to new items.

## Scoring System

Score determines retention and promotion at every stage.

The formula is: `score = weight * rate^tick_count`

- A new item starts with tick count zero, so its initial score equals its weight.
- Each tick reduces the score because rate is less than 1.0.
- Reusing an item resets its tick count to zero, restoring its score to the current weight.
- Weight blending on reuse: `new_weight = 0.7 * old_weight + 0.3 * llm_assessed_weight`. The original weight is favored to prevent oscillation.

Thresholds per stage:

- PFC: promote to hippocampus above 0.7, evict below 0.5
- Hippocampus: promote to neocortex above 0.7, forget below 0.3
- Neocortex: keep if final score above 0.6 at evaluation, otherwise forget

## Implementation Approach

### Phase 1: Core scoring and PFC

Build the scoring engine and in-memory ring buffer first. This is the foundation everything else depends on. Test the scoring formula, tick mechanics, weight blending, and eviction/promotion thresholds in isolation.

### Phase 2: SQLite persistence

Add the hippocampus and neocortex tables. Implement read/write operations with separate connections and WAL mode. The PFC stays in-memory; only hippocampus and neocortex persist.

### Phase 3: Writer pipeline

Wire up the full per-turn pipeline: receive context, run LLM analysis, update PFC, promote to hippocampus, evaluate and promote to neocortex. This is where the single LLM call per turn happens.

### Phase 4: MCP server and reader

Expose the reader as an MCP tool. Implement hybrid keyword + semantic search over the neocortex. At this point the system is usable end-to-end.

### Phase 5: Hook integration

Connect the post-turn hook so the writer fires automatically after each agent turn. The system is now autonomous.

## Key Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Runtime | Go, separate process | Decoupled from opencode, testable, easy to evolve |
| IPC | stdin/stdout JSON-RPC | Clean, simple, no daemon management |
| Persistence | SQLite (WAL mode) | ACID, queryable, well-supported in Go |
| Tool exposure | MCP server | Native opencode integration |
| PFC storage | In-memory ring buffer | Hot path, no disk I/O during scoring |
| Ticks | Global counter, 1 per agent turn | Simple, predictable decay |
| Content format | Plain text | LLM can understand anything |
| Error handling | Fail silently + log | Memory is non-critical, must not break agent |
| Writer LLM | Single call per turn | Balance of accuracy, latency, and cost |
| PFC matching | LLM semantic matching | Most accurate for determining reuse |
| Weight blending | 70/30 favor original | Prevents oscillation, preserves initial assessment |
| Project structure | Simple package | Start simple, restructure later if needed |

## Constraints (v1)

- No vector embeddings or semantic search backend. Keyword matching with statistical backup only.
- No configurable parameters via config file. Thresholds and rates are hardcoded constants.
- No test suite. Manual testing during development.
- No multi-session memory. Each turn is independent; the PFC is rebuilt from context each time.
- No memory editing or deletion by the user. Writes are automatic via the writer pipeline.
